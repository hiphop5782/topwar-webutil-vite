# 투표 히스토리와 최종 종료 보관

## 주소 및 저장 형식

- `/vote/create`: 생성. 메뉴에서는 숨기지만 직접 접속 가능.
- `/vote/cast/3223`: 서버별 목록, 생성일 최신순. 진행 중만 강조.
- `/vote/cast/3223/투표ID`: 상세. 기존 `/vote/cast/투표ID`, `/vote/3223/투표ID`도 유지.
- `/vote/manage/투표ID`: 기존 관리 화면.
- 숫자 1~6자리 단일 cast 경로는 서버 번호, 8자리 코드 및 UUID는 기존 투표 ID로 해석.
- 공개 저장소 `hiphop5782/topwar-vote`, `main` 브랜치.
- `3223/2026-09-22-001.json`: 한국 시간 최종 종료일 + 서버별 당일 순번.
- `3223/index.json`: 목록 요약. UUID를 유지하므로 파일명과 페이지 주소는 독립적.

## UID 및 스냅샷

새 투표(schemaVersion 2)는 생성 시 레벨 80 이상 대상자를 조사 데이터에서 추출하고 UID를 검증한다.
Firestore `votes/{id}/snapshots/roster`에 UID·닉네임·원시 CP(power)·길드 정보를 고정 저장한다.
응답은 UID 기준으로 변경/중복 판별한다. 직접 입력도 UID 필수. UID 입력은 본인 인증은 아니다.
신규/이동 인원은 직접 입력으로 참여할 수 있지만 생성 당시 대상 명단을 변경하지 않는다.
기존 투표의 누락된 UID/당시 명단은 추측하여 채우지 않는다. 보관 JSON에 rosterSource=unavailable로 표시하여 미래 통계에서 제외할 수 있게 한다.

## 상태

- active: 진행.
- paused (closed=true): 일시정지, 재개 가능. 기존 closed=true도 일시정지 취급.
- archiving: 최종 종료 확정, 재개/투표/삭제 금지. 원본 유지, 자동 보관 대기.
- archived: GitHub 결과 및 인덱스 검증 완료. Firestore에는 요약·관리 정보·보관 경로/커밋만 남고 응답 배열 및 스냅샷 삭제.

30일 자동 삭제는 제거했다. 기한 만료는 자동으로 공개 보관하지 않으며 관리자가 최종 종료를 선택해야 한다.
공개 파일은 허용 목록 필드만 직렬화한다. 비밀번호와 관리자 정보는 포함하지 않는다.
업로드/검증 실패 시 원본 유지, 다음 작업에서 재시도. 같은 UUID 재실행은 중복 파일을 만들지 않는다.
결과+index는 하나의 Git 커밋으로 저장하며 동시 충돌은 최신 HEAD를 읽어 재시도한다.
보관 후 GitHub 파일을 수동 변경하지 말 것. Firebase는 검증 당시 커밋을 가리킨다.

## 최초 운영 설정 (필수, 코드 배포만으로는 자동 보관되지 않음)

1. `hiphop5782/topwar-vote`를 공개 저장소로 만들고 README 등을 커밋하여 **main 브랜치를 초기화**한다.
2. 해당 저장소에만 Contents read/write 권한이 있는 fine-grained PAT를 발급한다.
3. 이 웹 프로젝트 저장소의 Actions Secret `VOTE_ARCHIVE_TOKEN`에 저장한다. VITE_ 환경 변수에 넣지 않는다.
4. `topwar-helper` 프로젝트 Firestore에 필요한 읽기/쓰기 권한을 가진 전용 서비스 계정을 준비하고 JSON 키를 Actions Secret `FIREBASE_SERVICE_ACCOUNT`에 저장한다. 최소 권한 사용 및 키 교체 정책을 적용한다. 저장소 파일에 커밋하지 않는다.
5. `.github/workflows/archive-votes.yml`을 기본 브랜치에 배포하고 Actions 실행을 허용한다. 설정/검증이 끝난 뒤 저장소 Actions Variable `VOTE_ARCHIVE_ENABLED`를 `true`로 설정한다. 기본값은 비활성화라 준비 전 예약 작업이 실패를 반복하지 않는다.
6. 아래 Firestore 규칙 점검 후 테스트 투표에서 생성·응답·일시정지·재개·최종 종료를 확인한다.
7. Actions에서 `Archive ended votes`를 수동 실행하여 JSON/인덱스, 원본 제거, 상세/기존 주소를 확인한다.

스케줄은 5분 간격이나 GitHub 사정에 따라 지연된다. 즉시 완료를 보장하지 않는다.
공개 저장소의 장기 비활성화로 예약 실행이 중지되거나 토큰 만료 시 Actions를 확인한다.
백엔드 서버는 추가하지 않지만 Actions 실행 시간/API 사용량과 Firestore 읽기/쓰기 비용은 발생한다.

## Firestore 보안 규칙 배포 전 점검

현재 프로젝트에는 운영 Firestore rules 파일이 없으므로 이 변경은 기존 규칙을 임의로 덮어쓰지 않는다.
**화면/클라이언트 검사는 보안 경계가 아니다.** 기존 비밀번호는 공개 투표 문서에 들어 있어 강력한 관리자 인증이 아니다.
운영 규칙에서 다음을 검증해야 한다:

- 스냅샷은 생성 시에만 작성 가능하고 일반 클라이언트 수정/삭제는 차단. 읽기는 상세 조회에 허용.
- archiving/archived 문서는 일반 클라이언트 응답/상태 수정/삭제 차단. 보관 worker의 서비스 계정만 정리 가능.
- 기존 규칙이 snapshot 하위 컬렉션을 허용하지 않으면 새 투표 생성 트랜잭션은 실패하며 반쪽 저장되지 않는다.
- 서버별 목록 조회 권한 확인. 쿼리는 serverId의 숫자/문자열 호환 단일 필드 in 쿼리.
- 신뢰할 수 있는 관리자 인증 없이는 최종 종료 권한을 강하게 보호할 수 없다. Firebase Auth 관리자 권한/서버 검증 도입이 권장된다.

실제 규칙과 관리자 인증은 운영 환경 확인·설정이 필요하다. 앱 코드만 바꾸었다고 악의적인 직접 DB 쓰기를 막는다고 가정하지 않는다.
공개 데이터에는 UID, 닉네임, CP, 개인별 선택이 포함된다. 생성/최종 종료 화면에 공개 안내가 표시된다.
